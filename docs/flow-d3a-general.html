D3A 和 General 到底怎么分

Domain 只在这里分叉

D3A Path

固定 Coding Layer：TRAN_CFG / DO / VISP_ADP / TFC_TFI / TFE / ADP / DRV
DT domain 先用 placeholder：TPRINT / FW / DPF
API Contract 必须先于 implementation。
完成条件：required DT domain 全 GREEN，并且 tran_build PASS。

General Path

普通 coding，不强塞 D3A 规则。
不编造团队 taxonomy，默认使用 GENERAL_COMPONENT_PLACEHOLDER。
只有 API / 外部行为 / 数据语义 / 错误语义 / 兼容性变化时，才升级 API Contract。
完成条件：task / verification contract 满足，required checks PASS。

fast / lite / complex 是什么

Lane 只表示执行强度
Lane 什么时候用 至少要验证什么
fast 简单明确、低风险、小范围、无核心行为变化。 验收检查、变更文件 review、basic verification evidence、completion summary。
lite 默认普通开发：范围可控，但需要认真验证。 task contract、focused plan、relevant context、test or build evidence、completion summary。
complex 跨模块、高风险、API 语义变化、多测试域、需要 dependency DAG。 detailed plan、knowledge gate、evidence plan、required tests/builds、review。

判断顺序：先看 complex hard trigger；再看 fast 是否全部满足；其他默认 lite。不确定就升级，不能降级省事。

知识什么时候加载

贯穿全程，不只在写代码时

Brainstorming / 澄清

OKL、repo rules、已有设计摘要、少量代码 anchor 都可以加载。目的：问对问题，不是证明完成。

Domain / Lane 判断

加载 D3A / General module、registry、lane policy。目的：选对路径和执行强度。

执行 / 验证

有 anchor 先 bounded grep；影响面不清楚再 targeted CodeGraph；无 anchor 但有 domain 可先 OKL。

OKL 是 LLM Wiki，适合查背景、规则、历史和关键词；grep 负责代码事实；targeted CodeGraph 负责影响面。OKL 不能替代 test / build / static check evidence。
