Intent Dynamic Code Workflow

这张图只表达一件事：用户输入先完成意图对齐；确认后自动进入 D3A Path 或 General Path；后续由证据闭环，不靠模型自信宣布完成。

人工确认点 自动闭环 D3A 专用路径 General 通用路径

1. 从用户输入开始

先判断输入成熟度，不先写代码
1

一句话 / 模糊想法

进入原版 Brainstorming 思路 + IDC overlay，产出可讨论的草案。

人看到：Brainstorming View

2

普通需求 / 半结构化描述

进入 intent-grilling，用 Grill Me 方式追问缺口、风险、验收口径。

人看到：Clarification View

3

TR3 / 设计文档

先抽取需求、DT 设计、约束和未知项，再少量追问关键冲突。

人看到：Clarification View

2. 对齐闸门

这里是主要人工 check 点
A

整理用户意图

把输入变成目标、范围、非目标、约束、验收标准、未知项。

B

判断场景类型

识别是新增需求、霰弹式修改、D3A 需求，还是 General coding。

C

形成 machine contract

生成机器可执行的合同，但不把完整 YAML 直接扔给用户。

D

Alignment View

用户只确认人能读懂的摘要、边界、风险、证据要求。

3A. D3A Path

只处理 D3A 场景
1
加载 D3A module

固定 Coding Layer：TRAN_CFG、DO、VISP_ADP、TFC_TFI、TFE、ADP、DRV。

2
声明 DT domain

V0 只保留 placeholder：TPRINT、FW、DPF；不猜内部真实实现。

3
先做 API Contract

API / task / verification contract 必须先于 implementation。

4
分 layer packet 开发

每阶段尽量控制在 500 行内，按 packet 产出 RED / GREEN evidence。

5
D3A 完成条件

required DT domain 全部 GREEN，并且 tran_build PASS。

3B. General Path

普通 coding / 非 D3A 场景
1
加载 General module

不编造组件分类；默认使用 GENERAL_COMPONENT_PLACEHOLDER 等占位符。

2
判断是否需要 contract

涉及 API、外部行为、数据语义、错误语义或兼容性时，才升级为 API Contract。

3
选择流程强度

Fast / Standard / Strict 由风险、影响范围、测试可得性和用户约束决定。

4
自闭环开发

所有 lane 都要有证据闭环；Fast 可用轻量测试或静态检查，Standard / Strict 更偏 TDD。

5
General 完成条件

task contract、verification contract、required checks 和 completion summary 都满足。

4. 确认后自动闭环

一开始对齐，后面自动跑
1

Plan Packet

按 500 行左右的阶段切分，先列证据目标，再动代码。

2

Implement

小步修改，保持 domain module 和 contract 对齐。

3

Verify Evidence

TDD 场景必须有 RED evidence 和 GREEN evidence；非 TDD 也必须有工具证据。

4

Completion View

展示改了什么、证据在哪里、剩余风险是什么。

5. 知识工具怎么配合

OKL / grep / targeted CodeGraph
有代码 anchor 先 bounded grep 定位真实代码，再按需 targeted CodeGraph 看调用影响，最后用 OKL 查规则或历史。
无 anchor，有 domain 先 OKL 取摘要 / refs / keywords，再 bounded grep 找代码锚点，必要时 targeted CodeGraph。
无 anchor，无 domain 先 Discovery / Grilling 把意图问清楚，再选择 OKL 或 grep。

OKL 是 LLM Wiki，适合拿背景、规则、历史和关键词；grep 是代码事实定位；targeted CodeGraph 是结构和影响面分析。OKL 不能覆盖代码事实，最终完成仍然看 test / build / static check 的工具证据。

  • 人工 check 点主要在 Alignment View。
  • 中途发现 contract 冲突或证据无法完成，才进入 Escalation View。
  • D3A 与 General 是 domain module 分流，不互相抢规则。
