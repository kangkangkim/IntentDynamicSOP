Intent Dynamic Code Workflow

这版按“层”来看：上层只负责把用户意图对齐清楚；中层选择 D3A Path 或 General Path；下层执行、检索和证据闭环。人工主要卡在 Alignment View，approve 后尽量自动完成。

人工对齐层 Domain 层 自动执行层 知识检索层
1. 用户输入层 决定从哪里进入 workflow

一句话 / raw idea

先进入 Brainstorming View，把模糊想法扩成 draft spec。

普通需求

直接进入 Grill Me 收敛，补齐目标、范围、验收和风险。

TR3 / 设计文档

抽取需求、DT 设计、约束、接口和未知项，再追问冲突。

本层可能加载的知识

OKL 用于理解术语、业务背景和历史规则；如果输入自带文件名、接口名、错误日志，则用 bounded grep 建立代码 anchor。

↓
2. 意图对齐层 先问清楚，再允许写代码

intent-discovery

raw idea 使用原版 Brainstorming 思路，并加 IDC overlay 做交接。

intent-grilling

Grill Me 风格追问关键缺口，尤其是验收、边界和风险。

Requirement Assessor

判断信息是否足够进入 Domain / Lane / Contract。

Alignment View

用户确认目标、范围、非目标、完成标准和升级条件。

本层可能加载的知识

Brainstorming / 澄清会查 OKL、repo rules、已有设计摘要和少量代码 anchor，目的只是帮助问对问题，不作为完成证据。

↓
3. Domain 分流层 D3A 与 General 在这里分开

3A. D3A Path

专用 module
1
固定 D3A Coding Layer

TRAN_CFG / DO / VISP_ADP / TFC_TFI / TFE / ADP / DRV

2
DT domain 是 placeholder

TPRINT / FW / DPF，真实映射进保密区后填写。

3
API Contract 先于实现

D3A spec、API contract、task contract、verification contract 必须先齐。

4
D3A done

required DT domain 全 GREEN，并且 tran_build PASS。

3B. General Path

通用 coding module
1
不编造 taxonomy

默认使用 GENERAL_COMPONENT_PLACEHOLDER 等占位符。

2
按需 API Contract

API、外部行为、数据语义、错误语义或兼容性变化时才启用。

3
选择流程强度

fast / lite / complex 由风险、影响面、测试可得性和约束决定。

4
General done

task / verification contract 满足，required checks PASS。

本层可能加载的知识

Domain 分流会读取 domain module、registries、AGENTS.md / repo rules；有真实代码 anchor 时才用 grep 或 targeted CodeGraph 校验影响面。

↓
4. 执行编排层 approve 后进入自动计划与实现

Plan Packet

把任务拆成阶段，每个阶段尽量控制在 500 行左右。

Constraint Loading

只加载当前 packet 需要的规则、contract 和 domain module。

Implementation

小步修改，保持代码、contract、验证目标一致。

Escalation View

范围变化、证据不可得、contract 冲突时回到人工确认。

Lane Resolver

只判断执行强度，不判断领域。先看 complex hard trigger，再看 fast 准入条件，其他默认 lite。

fast 小闭环

适合简单明确、低风险、小范围任务；至少要有验收检查、变更文件 review、basic verification evidence 和 completion summary。

lite 标准闭环

默认中间态；需要 task contract、focused plan、relevant context、test or build evidence 和 completion summary。

complex 强闭环

跨模块、高风险、API 语义变化、多个测试域或需要 DAG 时进入；需要详细计划、knowledge gate、完整 evidence plan 和 review。

本层可能加载的知识

执行时按 packet 渐进加载约束、邻近代码、调用关系、测试入口；避免一次性加载全仓或长日志。

↓
5. 证据闭环层 完成只能由 evidence 决定

RED Evidence

TDD 场景必须先看到失败证据，不能直接声称 GREEN。

GREEN Evidence

测试、build、static check 或 domain-specific command 必须 PASS。

Completion View

展示改了什么、验证了什么、证据引用和剩余风险。

不能完成

缺工具证据、缺 contract 或 scope 改变时必须升级，不靠自信收尾。

本层可能加载的知识

验证阶段可以加载测试规则、build 约束和失败摘要；OKL 只能解释背景，不能替代 test / build / static check evidence。

贯穿式知识检索层

知识不是只在执行阶段加载，而是按阶段、按目的、按最小必要范围加载。

Brainstorming

OKL / 设计摘要帮助扩展可能方案和识别术语。

澄清 / Grill Me

OKL、repo rules、已知 anchor 帮助提出关键问题。

Alignment View

加载 contract、约束、风险和证据要求，给用户确认。

Domain / Lane

加载 D3A / General module、registry、lane policy。

执行 / 验证

bounded grep 定位事实，targeted CodeGraph 看影响，OKL 查背景；最终以工具证据收尾。

Provider 顺序：有 anchor 先 bounded grep；无 anchor 但有 domain 先 OKL；影响面不清楚再 targeted CodeGraph。
