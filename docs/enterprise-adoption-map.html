领域注册表

真实 DT Domain、GC 组件、测试域清单。

domain: / general: d3a.dt_domains / components / test_domains
  • 条目形如 {id, knowledge_ref}
  • 非空列表整体替换仓库注册表
  • 留 [] 用仓库 V0 placeholder
domain:
  d3a:
    dt_domains:
    - id: DT_DEMO
      knowledge_ref: docs/dt/DT_DEMO.md
# 填了这 1 条，TPRINT/FW/DPF 整个被替换
Domain / Knowledge Gate 替换 dt-domains.yaml 等注册表（不合并）
  • Planner 只能从替换后的清单选 DT Domain
  • Knowledge Gate 只加载受影响域的 knowledge_ref
  • D3A 7 层固定，不走这条通道
内部 Skill 能力池

公司已有 Brainstorming、GC SOP 原子能力、dt-design / dt-writer、impl review 等 skill。

bindings.*.skill_ref 20 个槽位全部绑定 skill_ref，按能力语义对号入座
  • brainstorming / ut_design / impl_review / tdd_workflow ...
  • dt_design / dt_writer / dt_build / tran_build 同为 skill 槽（见下行）
  • 没有的能力留 null
bindings:
  impl_review:
    skill_ref: /repos/demo-skills/impl-review.md
  brainstorming:
    skill_ref: .claude/skills/idc-brainstorming/SKILL.md
# skill_ref 可为 harness 相对路径或绝对路径
Skill Adapter Router 按 registry eligibility 匹配，不按名字猜
  • stage + capability key + contract + blocks_when 全匹配才触发
  • 公司 skill 输出归一化成 IDC contract / evidence
未配置时：无 registry row 匹配 -> NEEDS_ADAPTER_MAPPING
构建与验证系统

真实 DT build / run、tran_build 和 PASS 判定，封装在企业 skill 里。

bindings 构建槽（同为 skill 槽） 绑定企业 build skill，配置里永远不出现命令
  • dt_build.skill_ref / tran_build.skill_ref
  • 没有现成 build skill？先把真实命令包成极小 wrapper skill（跑命令、回传日志 / exit code），再绑定
bindings:
  dt_build:
    skill_ref: /repos/demo-skills/dt-build.sh
  tran_build:
    skill_ref: /repos/demo-skills/tran-build.sh
idc-dt-build / idc-tran-build 委托绑定的企业 skill 执行，产出 evidence
  • 命令封装在 skill 内部，harness 只见 skill_ref
  • RED / GREEN / PASS 只认工具输出，不认模型自信
  • 失败交给 build-error-analyzer 生成 targeted fix task
未配置时：槽位为 null -> NEEDS_TEAM_CONFIG，产不出真 evidence -> 到不了 DONE
领域知识库

架构文档、Layer 文档、verification mapping、repo context provider。

knowledge: 只填 ref，不搬正文
  • architecture_doc_ref / feature_docs_root_ref
  • layer_docs: {LAYER: ref}
  • verification_mapping_ref / repo_context.provider_skill_ref
knowledge:
  layer_docs:
    TFE: /repos/demo-docs/layers/TFE.md
  verification_mapping_ref: /repos/demo-docs/verify-map.md
Layer Context Packet 渐进加载，一次只装当前 Layer
  • 知识正文留在企业本地，harness 只存地址
  • 无 anchor 时按领域语义选 provider，不靠猜
未配置时：Knowledge Gate 判定知识不足 -> 阻断 coding
流程偏好

默认执行强度和允许跳过的步骤。

lane: Lane default + Capability Selection
  • default: fast / lite / complex（仅 dynamic-lane route）
  • Fast 1 / Lite 3 / Complex dynamic optional skill budget
lane:
  default: lite             # D3A 忽略此值，采用固定 workflow
  default: lite
Lane Resolver Lane 只决定流程跑多重
  • D3A module 标记 Lane 不适用并跳过 Resolver
  • Complex hard trigger 仍直接进 complex
  • 跳步不能绕过 API Contract 和 RED / GREEN

0 入区前

  1. 复制 harness 进保密区
  2. python3 tests/test_harness.py 全绿
  3. 确认无企业 secret 混入
例：输出 45 个测试通过 才算过。

1 填一个文件

  1. cp template -> team-config.yaml
  2. 按上表左列资产对号填中列插槽
  3. 再跑 harness：填错的就地校验变红
例：最小可用 = config_version + team 两项 + domain.mode + 必需 skill_ref。可用 交互式生成器填表生成。

2 过 Readiness Gate

  1. 跑 vertical-slice-readiness gate
  2. 看 BLOCKED 清单还缺哪个 binding
  3. gate 只证明能启动，不替代 evidence
例：BLOCKED 项 tran_build skill 未绑定 -> 回第 1 步补。

3 第一条 vertical slice

  1. 1 个 Layer + 1 个 DT Domain
  2. freeze API Contract -> RED -> GREEN
  3. tran_build PASS -> Completion Summary
例：TFE 层 × DT_DEMO：RED ref -> GREEN ref -> tran_build PASS。

4 扩展与复用

  1. 逐步加 Layer / DT / GC 组件
  2. 第二团队：另一个 team-config.yaml
  3. 非 D3A 领域：复制 template-domain/ 模块
例：第二团队只改 team.id / repo_path，skill 池共用。

企业要准备什么

  • 一个可访问的代码仓路径
  • 内部 skill 清单与存放根目录
  • 真实 DT / tran_build 能力（企业 skill，命令封装在 skill 内部）
  • 领域知识地址（不搬正文）

harness 不改什么

  • IDC Core：router / gate / lane / schema
  • D3A 7 层固定架构
  • Skill Adapter registry 的 eligibility 规则
  • 验证门：API Contract 先行、RED 先于 GREEN

生效怎么保证

  • 首读链路：workflow 启动先加载 team-config
  • 静态校验：harness 测试就地检查填好的配置
  • 显式失败：缺配置返回状态码，不静默跳过
  • 证据门：没有真实 evidence 到不了 DONE

常见失败信号

  • NEEDS_TEAM_CONFIG：必需槽位还是 null
  • NEEDS_ADAPTER_MAPPING：registry 无匹配行
  • Readiness Gate BLOCKED：binding 不足
  • 测试红：残留 <占位符> 或 ref 指向不存在
