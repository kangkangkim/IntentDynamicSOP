一份配置，四道机器约束

团队只维护 team-config.yaml。系统把它编译成有序执行图，再由宿主授权、调度和完成验证强制兑现。

版本边界：根 team-config.yaml 当前仍走 v1 compatibility；v1 支持迁移预览，但 v1 compatibility 不要求 v2 graph 或 host-control。要获得下图的确定性强制链，请使用 v2。

YAML 为何一定被遵从：8 个真实实现关卡

保证的准确含义不是任意 YAML 都能成功；保证的是：有效配置无法被静默忽略。字段必须被消费并进入相互绑定的机器产物；无消费者、非法值、字节漂移或绕过任一关卡，都不能到达 DONE。

桌面端从左向右读取；移动端自动改为从上到下。每关都明确回答“读什么、调用谁、写出什么、哪里拒绝”。

配置权属与覆盖规则

团队只改一处

domains.enabled/default/definitions、Lane override、bindings、adapter_extensions、alignment 和 knowledge ref 只来自 team-config.yaml。

Pack 提供默认值

Pack 拥有 workflow、capability、registry 与 completion policy。definition 可替换对应 ref；省略字段保留 Pack 默认。

.idc/ 不是配置

effective runtime、selection、graph、authorization 和 ledger 都是可重建派生产物，不能成为第二配置源。

registry 的显式值整体替换，不做 merge；团队 Lane 只覆盖同名 Pack Lane；bindings.<capability>.skill_ref 替换原子 Skill ref；extension 只能新增原子能力。

从准备到 DONE 的真实闭环

  1. prepare_runtime.py 生成 READY runtime。
  2. plan_context.py、plan_knowledge.py、select_capabilities.py 绑定同一 execution unit。
  3. compile_run_graph.py 固化全部 ordered occurrences。
  4. 真实 v2 graph authorization 要求宿主在 executor 不可写路径创建 control record；v1 compatibility 不要求。
  5. 宿主通过 dispatch_state.py Python API 调用 initialize_state / acquire_dispatch / record_success / record_predicate / export_snapshot；它不是 CLI。
  6. run_event_ledger.py replay，verify_completion.py 读取 protected dispatch state / predicate attestation 后判断 DONE。
python3 .claude/skills/idc-team-config/scripts/prepare_runtime.py --config team-config.yaml

D3A 删除边界与宿主信任边界

从 domains.enabled 省略 d3a 即禁用：Core 不加载或物化 D3A 资产；物理移除未启用的 D3A Pack 不影响 General / Custom；显式启用但 Pack 缺失则有界失败。

host control 管“能不能派发”

绑定 authorization 输入、graph、node、scope 与 executor。request 内嵌声明不能自证或扩权。

dispatch-state predicate 管“能不能完成”

普通 node success 不能替代 predicate PASS。两类记录都必须位于 executor 不可写的宿主保护路径。

SHA-256 只证明字节完整性，不是签名或身份认证；本架构不承诺非幂等下游的 exactly-once。非目标还包括签名服务、企业私有实现和第二份团队配置。
